# 3. 하드웨어와 OS: 락의 바닥

자바 락의 동작과 비용은 결국 CPU와 OS가 정합니다. 예제 주석에 나오는 `lock cmpxchg`, 캐시 라인, futex 같은 말을 여기서 정리합니다.

## 3.1 메모리 계층

| 위치 | 접근 시간 (대략) | 범위 |
|---|---|---|
| 레지스터 | < 1ns | 코어 하나 |
| L1 캐시 | ~1ns | 코어 하나 |
| L2 캐시 | ~3–5ns | 코어 하나 (또는 몇 개) |
| L3 캐시 | ~10–20ns | 소켓 전체 공유 |
| 메인 메모리 (DRAM) | ~80–100ns | 전체 |

메모리가 캐시보다 수십 배 느리기 때문에 CPU는 최대한 캐시에서 일합니다. 그래서 "어떤 코어의 캐시에 어떤 값이 있는가"가 동시성의 출발점입니다.

## 3.2 캐시 라인과 일관성 (MESI)

- 캐시는 바이트 단위가 아니라 **캐시 라인**(x86·ARM 대부분 64바이트) 단위로 메모리를 가져옵니다.
- 여러 코어가 같은 라인을 캐시하므로, 하드웨어가 **캐시 일관성 프로토콜**로 맞춥니다. 대표가 MESI입니다.

| 상태 | 의미 |
|---|---|
| **M**odified | 이 코어만 가지고 있고, 메모리와 다르게 수정됨 |
| **E**xclusive | 이 코어만 가지고 있고, 메모리와 같음 |
| **S**hared | 여러 코어가 읽기 전용으로 가짐 |
| **I**nvalid | 무효. 다시 가져와야 함 |

어떤 코어가 라인에 쓰려면 먼저 **다른 코어들의 복사본을 Invalid로 만들고** 자기가 Modified를 가져야 합니다. 이 메시지 교환은 코어 사이를 오가므로 수십~수백 사이클이 걸립니다.

여기서 동시성 비용 두 가지가 나옵니다.

- **캐시 라인 핑퐁:** 여러 코어가 같은 변수에 번갈아 쓰면, 그 라인이 코어 사이를 계속 오갑니다. 락의 `state` 필드, `AtomicInteger`의 값이 경합이 심할 때 느려지는 이유입니다(`CasCounter`).
- **거짓 공유(false sharing):** 서로 다른 변수라도 같은 캐시 라인에 있으면, 한쪽 쓰기가 다른 쪽 라인까지 무효화합니다. `LongAdder`는 셀마다 `@Contended`로 패딩을 둬서 이를 피합니다(`HitCounter`). JDK 내부가 아닌 코드에서 `@Contended`를 쓰려면 `-XX:-RestrictContended`가 필요합니다.

**일관성(coherence)과 메모리 모델은 다른 문제입니다.** MESI는 "한 주소에 대해 모든 코어가 결국 같은 값을 본다"는 것만 보장합니다. 여러 주소에 대한 쓰기가 **어떤 순서로** 보이는지는 다음 절의 스토어 버퍼 때문에 따로 다뤄야 합니다.

## 3.3 스토어 버퍼와 재정렬

쓰기마다 다른 코어의 무효화 응답을 기다리면 너무 느립니다. 그래서 코어는 쓰기를 일단 **스토어 버퍼**에 넣고 바로 다음 명령으로 넘어갑니다. 버퍼의 쓰기는 나중에 캐시로 내려갑니다.

| 순서 | 코어 0 | 코어 1 |
|---|---|---|
| 1 | `a = 1` → 자기 스토어 버퍼에 들어감 (캐시에는 아직 0) | `b = 1` → 자기 스토어 버퍼에 들어감 (캐시에는 아직 0) |
| 2 | `r1 = b` → 캐시에서 읽음: **0** | `r2 = a` → 캐시에서 읽음: **0** |
| 3 | 버퍼의 `a = 1`이 캐시로 내려감 | 버퍼의 `b = 1`이 캐시로 내려감 |

각 코어는 자기 스토어 버퍼를 볼 수 있지만, 다른 코어의 버퍼는 볼 수 없습니다. 그래서 [2장](02-java-memory-model.md#21-왜-필요한가-코드는-쓴-순서대로-실행되지-않는다)의 `r1 == r2 == 0`이 실제로 일어납니다. 쓰기가 뒤의 읽기보다 늦게 보이는 **StoreLoad 재정렬**입니다.

| CPU | 허용하는 재정렬 |
|---|---|
| x86-64 (TSO, Total Store Order) | StoreLoad만. 쓰기끼리, 읽기끼리의 순서는 지켜짐 |
| ARM64, POWER | 거의 모든 조합 (약한 메모리 모델) |

## 3.4 메모리 배리어

배리어(fence)는 "이 지점 앞뒤의 메모리 접근 순서를 바꾸지 마라"는 명령입니다.

| 명령 | 효과 |
|---|---|
| x86 `mfence`, 또는 `lock` 접두 명령 | 스토어 버퍼를 비울 때까지 기다림 (full fence) |
| ARM64 `dmb ish` | full fence |
| ARM64 `ldar` / `stlr` | 각각 acquire 읽기 / release 쓰기 |

HotSpot은 x86에서 volatile 쓰기 뒤에 `mfence` 대신 `lock addl $0,(rsp)`를 씁니다. 스택에 0을 더하는 아무 의미 없는 명령이지만, `lock` 접두 덕분에 full fence 효과가 있고 `mfence`보다 빠르기 때문입니다.
자바 코드에서 직접 배리어를 쓸 일은 거의 없습니다. `volatile`, 락, `Atomic*`, `VarHandle`이 알맞은 배리어를 넣어 줍니다.

## 3.5 원자 명령

락과 `Atomic*`의 바닥은 CPU가 제공하는 **읽기-수정-쓰기를 한 번에 하는 명령**입니다.

| 연산 | x86-64 | ARM64 |
|---|---|---|
| CAS (compare-and-swap) | `lock cmpxchg` | `cas`/`casal` (ARMv8.1 LSE), 또는 `ldaxr`/`stlxr` 루프 |
| fetch-and-add | `lock xadd` | `ldadd` (LSE) |
| swap | `xchg` (항상 lock 의미) | `swp` (LSE) |

- x86의 `lock` 접두는 그 캐시 라인을 Modified 상태로 붙잡은 채 읽기·비교·쓰기를 끝냅니다. 그동안 다른 코어는 그 라인에 접근하지 못합니다.
- ARM의 LL/SC(`ldaxr`/`stlxr`)는 "읽은 뒤 아무도 안 썼으면 쓰기 성공"이라서, 실패하면 소프트웨어가 다시 시도합니다.
- **경합이 없으면 CAS는 수십 사이클입니다.** 경합이 있으면 3.2의 캐시 라인 이동 비용이 붙습니다. 그래도 OS가 관여하지 않으므로 스레드를 재우는 것보다는 훨씬 쌉니다.

자바의 모든 락(모니터의 thin lock, AQS의 `state`)은 경합이 없을 때 **CAS 한 번**으로 획득됩니다. "락은 느리다"는 말은 대부분 **경합이 있을 때** 이야기입니다.

## 3.6 스핀 vs 블로킹

락을 못 얻은 스레드에게는 두 가지 선택지가 있습니다.

| | 스핀 (busy-wait) | 블로킹 (잠들기) |
|---|---|---|
| 방법 | 루프를 돌며 계속 확인 | OS에 재워 달라고 하고 깨워 줄 때까지 대기 |
| 비용 | 코어를 계속 씀 | 컨텍스트 스위치 2번 (수 μs) + 캐시 손실 |
| 유리할 때 | 락이 곧 풀릴 때 (임계 구역이 짧을 때) | 오래 기다려야 할 때 |

그래서 실제 구현은 **둘을 섞습니다.**

- **모니터:** 적응형 스핀(adaptive spinning). 지난번에 스핀으로 성공했던 락이면 더 오래 스핀하고, 아니면 금방 포기하고 잠듭니다.
- **AQS:** 대기 큐에 들어간 뒤 잠깐 스핀하고 나서 `park()`합니다.
- 스핀 루프 안에서는 `Thread.onSpinWait()`를 부릅니다. x86에서는 `pause` 명령이 되어, 하이퍼스레딩 짝 코어에 자원을 양보하고 전력을 아낍니다.

## 3.7 OS의 대기: futex

스레드를 재우고 깨우는 건 OS 커널만 할 수 있습니다. 하지만 시스템 콜은 비싸므로(사용자 모드 ↔ 커널 모드 전환), Linux는 **futex**(fast userspace mutex)라는 방식을 씁니다.

1. 락 상태는 **사용자 공간의 정수 하나**입니다. 경합이 없으면 CAS로 그 정수만 바꾸고 끝납니다. **커널에 가지 않습니다.**
2. 경합이 생겼을 때만 `futex(FUTEX_WAIT, 주소, 기대값)` 시스템 콜로 커널에 "이 주소의 값이 아직 기대값이면 나를 재워 줘"라고 요청합니다. 커널은 주소별 대기 큐에 스레드를 넣고 스케줄러에서 뺍니다.
3. 해제하는 쪽은 대기자가 있을 때만 `futex(FUTEX_WAKE, 주소, n)`로 n개를 깨웁니다.

"값이 아직 기대값이면"이라는 확인을 커널이 원자적으로 하기 때문에, 확인과 잠들기 사이에 깨우기 신호가 사라지는 문제가 없습니다.

HotSpot은 futex를 직접 부르지 않고 `pthread_mutex`/`pthread_cond`를 쓰는데, glibc가 이것을 futex로 구현합니다.

| 자바 | HotSpot | Linux | Windows |
|---|---|---|---|
| `synchronized` 대기 | `ObjectMonitor` → `ParkEvent` | `pthread_cond_wait` → futex | 이벤트 객체 + `WaitForSingleObject` |
| `LockSupport.park` (AQS 전체) | `Parker` | `pthread_cond_wait` → futex | 이벤트 객체 + `WaitForSingleObject` |

자바 락이 "사용자 공간에서 CAS로 빠르게, 경합 시에만 커널로"라는 구조인 것도 같은 생각을 따른 것입니다.

## 3.8 정리: 락 획득 한 번에 일어나는 일

`ReentrantLock.lock()`을 예로, 경합 정도에 따라 비용이 이렇게 달라집니다.

| 상황 | 일어나는 일 | 비용 (대략) |
|---|---|---|
| 경합 없음 | `state` CAS 한 번 (`lock cmpxchg`) | 수십 ns 이하 |
| 경합 있음, 곧 풀림 | CAS 실패 → 큐에 들어감 → 잠깐 스핀 → 획득 | 수백 ns, 캐시 라인 이동 |
| 경합 있음, 오래 걸림 | 스핀 실패 → `park()` → futex로 커널 대기 → 해제자가 `unpark()` → OS가 다시 스케줄링 | 수 μs 이상 + 캐시 손실 |

락을 빠르게 쓰는 요령은 결국 **경합을 줄이는 것**입니다. 임계 구역을 짧게 하고, 읽기를 공유하고(`ReadWriteLock`, `StampedLock`), 쓰기를 분산시키는(`LongAdder`) 것이 모두 이 목적입니다.
